# 0.22.2 candidate — atomic draft registration

Both draft preparation workflows now use `reply_review.register_draft`. Validation finishes outside the writer transaction. The helper acquires SQLite's writer reservation with `BEGIN IMMEDIATE`, rechecks existing drafts by owner, record kind and unchanged `draft_key`, then captures all winning freshness markers and appends on the same connection. No marker capture or save occurs outside that transaction. A retry returns the saved draft unchanged and does not advance its boundary. Atomic review acceptance from 0.22.1 remains in place.

Existing duplicate drafts are preserved. Registration consistently chooses the first matching draft in the established stored ordering, keeping that draft's original ID, markers, wording and review history. Other historical draft IDs retain their own markers and exact review histories; reviews are not merged or reassigned. Distinct content and disclosure policies retain distinct keys. No schema migration, historical rewrite or renderer-authored findings are introduced.

Developer-facing skills/agent instructions, cost accounting, compliance, disclosure controls, and cache/compaction tools remain unchanged. The updated candidate is built only after affected tests, the full offline suite and clean-extraction checks pass. It is local only; no push or distribution is authorized. No Claude command or model invocation is performed.

## Regression evidence

The new tests use separate spawned processes and actual SQLite persistence. A forwarding append hook observes the captured marker values and pauses the older nontransactional writer while a second process records later access and prepares. It always delegates to the real append; no draft IDs or persistence outcomes are fabricated. Under the new writer reservation, competing access writes wait for commit and registration reuses the winner. The race covers single-session, combined collection and individual collection modes.

The identical-preparation race test fails against prior commit `56cce4a` in both workflows, producing two persisted drafts with the same key. The expected failures are retained in `.analysis/draft-registration-negative-control.log`, not counted as passes. The new implementation's tests also cover reopen/retry marker preservation, distinct content/policies under concurrency, rejection of pre-boundary reads, retained rejected/accepted review history, canonical selection of historical duplicates without merging their reviews, and rollback after an actual SQLite insert failure. The extracted MCP check repeats preparation before and after a synthetic accepted review and verifies unchanged draft, markers and accepted reply.

The affected run passed **62 tests**; the full offline suite discovered **411 tests: 409 passed and two optional private-corpus checks skipped**. The separate clean-extraction/package-process run passed **7 tests**. All 11 skill, reviewer-instruction, readout and pricing files checked against `56cce4a` remain byte-for-byte unchanged. The negative-control records were also checked to confirm one common key and different markers in each pair. Evidence locations and candidate checks are recorded in [validation](validation.md). Test evidence, synthetic race stores, private logs, generated reports and archives stay outside Git and the plugin package.

## Remaining release blockers

Final-package live checks remain **pending** for single-log, combined-log, separate-output and interrupted-review/resume flows, until the user explicitly confirms Claude limits reset. Inspect actual host Agent launches, paid reviewer invocation counts, source-review provenance and resumed draft/markers/history in those tests. Atomic draft registration does not establish a single paid reviewer launch: concurrent callers may still receive `review_required` for the same draft, and this change does not implement a reviewer-launch lease. Offline synthetic submissions are not a native-host or semantic-quality pass. No prior live pass is claimed for this candidate.
